# Restaurant CSV → Production Dataset: Implementation Plan

> **Scope**: Replicable, idempotent pipeline for `input/restaurants.csv` and any future CSV with the same schema. Stages match the steering doc: Ingest → Clean → Deduplicate → Fill & Transform → Validate → Publish → Notify, collapsed into 5 implementation steps.
>
> **Effort sizing**: Large (>500 lines, multi-module). Apply full quality gate per `workflow-and-quality.md`.
>
> **Tech stack** (locked in here so future steps don't re-debate):
> - Python 3.12, `uv` for env/lockfile, `just` for task running
> - **Polars** for all dataframe ops (lazy where possible)
> - **Pydantic v2** for config + row-level schema models
> - **Patito** (Polars-native Pydantic) for dataframe schema validation at stage boundaries
> - **rapidfuzz** for string similarity, **unidecode** for transliteration, **phonenumbers**-style normalization not needed (no phones in schema)
> - **pygeohash** for geo bucketing, **reverse_geocoder** (offline, no network) for lat/lng → city/state fallback
> - **structlog** for JSON logs with run_id correlation
> - **OpenAI Python SDK** (configurable provider; behind a `LLMClient` interface) for fill + cuisine + romantic scoring agents, with **diskcache** keyed by content hash for idempotency and cost control
> - **typer** for CLI, **pyyaml** for config, **python-dotenv** for secrets
> - **pytest** + **hypothesis** for unit/property tests

## Step 1 — Project scaffold, config, ingestion (Stages 1)

**Goal**: A runnable `just pipeline run --input <csv> --output <dir>` that loads the CSV into a typed Polars LazyFrame and emits a stage-1 artifact, with config, secrets, logging, and tests wired up.

**Deliverables**
- Repo layout matching the steering doc:
  ```
  pipelines/restaurant_pipeline.py      # orchestrator, one function per stage
  src/revel/
    config.py                           # Pydantic Settings, YAML+env merge
    io_csv.py                           # ingestion
    schemas.py                          # Patito models for each stage boundary
    logging_setup.py                    # structlog config, run_id propagation
    cli.py                              # typer entrypoint
  configs/local.yaml                    # default config; no secrets
  .env.example                          # OPENAI_API_KEY=, LLM_PROVIDER=openai, LOG_LEVEL=INFO
  tests/unit/                           # mirrors src/
  tests/integration/test_pipeline.py    # end-to-end on a 20-row fixture
  tests/fixtures/restaurants_sample.csv
  justfile                              # setup, lint, typecheck, test, pipeline-run
  pyproject.toml                        # uv-managed deps; ruff + mypy strict
  .gitignore                            # excludes .env, output/, .cache/
  README.md                             # quickstart
  ```

**Ingestion specifics**
- Read with `pl.scan_csv` (lazy), explicit `schema_overrides`:
  - `id: Int64`, `latitude/longitude: Float64`, all others `Utf8`.
  - `null_values=["", "null", "NULL", "None"]`, `infer_schema_length=0`, `try_parse_dates=False`.
  - `quote_char='"'`, `truncate_ragged_lines=False` so malformed rows fail loudly.
- Wrap in `read_restaurants(path) -> pl.LazyFrame` returning a frame validated against `RawRestaurant` Patito model (only column presence + types — no value rules yet).
- Compute and log: row count, null count per column, distinct count for `price_point`, `primary_type`, `city`. Persist as `output/<run_id>/01_ingest_stats.json` for the run report.
- Stage output: `output/<run_id>/01_raw.parquet` (snapshot for debuggability). Use `zstd` compression.

**Config strategy**
- `Settings(BaseSettings)` loads `configs/local.yaml`, then overlays `.env`, then CLI flags. Fields:
  - `input_path`, `output_dir`, `llm_provider`, `llm_model`, `llm_max_concurrency` (default 4), `llm_cache_dir`, `dedup_thresholds` (see Step 3), `cuisine_taxonomy_path`, `dry_run` (skip LLM calls, use stubs).
- Secrets only via env (`OPENAI_API_KEY`); never in YAML or logs. `Settings.model_dump()` redacts secret-tagged fields before logging.

**Quality gates for this step**
- `ruff check`, `ruff format --check`, `mypy --strict`
- Tests: schema mismatch raises, malformed CSV raises, run_id propagates through logs, fixture loads to expected row count.

**Risks / mitigations**
- *Embedded commas in `display_address`*: handled by quoted fields — verified by sample (e.g., `"229 South 4th Street, Brooklyn"`). Add a unit test using a row with a comma-laden quoted address.
- *Encoding surprises*: force `encoding="utf8"`; on `UnicodeDecodeError`, fail with actionable message naming the offending byte offset.

## Step 2 — Clean & normalize (Stage 2)

**Goal**: Deterministic, side-effect-free transforms that put every column into a canonical form so dedup and fill stages have a clean substrate. No LLM calls here.

**Per-column rules** (all implemented as small pure functions in `src/revel/clean.py`, composed in a single `clean(lf) -> pl.LazyFrame`):

| Column | Transform |
|---|---|
| `name` | `unidecode` → strip → collapse whitespace → strip leading articles (`The `, `the `) into a separate `name_core` column for matching while keeping original `name`. Title-case only if input is fully upper or fully lower (preserve mixed-case originals like `n/naka`). |
| `city` | Trim, strip surrounding quotes. Map known variants to a canonical set (`"Washington, DC"` ↔ `Washington, DC`, `"San Francisco Bay Area"` kept as-is). Build `city_canonical` from a YAML lookup at `configs/cities.yaml`; unknown cities pass through and are logged as warnings. |
| `display_address` | Trim, collapse whitespace, strip trailing `, USA`/`, United States`. Extract `state_code` (US 2-letter, regex `\b([A-Z]{2})\b\s*\d{5}`) and `postal_code` (regex `\b\d{5}(-\d{4})?\b`) into new columns. Original preserved. |
| `google_place_id` | Trim. Validate against `^[A-Za-z0-9_-]{20,}$` AND starts with a known prefix (`ChIJ`, `GhIJ`, `EkY`, `EhY`, `EiY`, `Ei0`). Anything failing → set to null + record reason in a `_quality_flags` list column. *(Confirmed by inspection: real entries are ChIJ-prefixed; fabricated/typo'd ones in the CSV will be filtered.)* |
| `latitude`, `longitude` | Cast to f64. Reject if outside continental US + HI/AK/PR bbox (`lat ∈ [17, 72]`, `lon ∈ [-180, -65]`). Reject pairs of exact `0.0, 0.0`. Set rejected to null + flag. |
| `price_point` | Map to `{low, medium, high, null}`. `budget` → `low`, `unknown` → null, `null`/empty → null. Anything else → null + flag. |
| `primary_type` | Lowercase, snake_case (already mostly is). Strip trailing `_us`/`_restaurant_us` suffixes into a `region_hint` column for the cuisine step. |
| `website` | Canonicalize via `urllib.parse`: lowercase scheme+host, strip `www.`, drop fragments, drop tracking query params (`utm_*`, `gclid`, `fbclid`, `scid`, `y_source`, `ecid`, `icid`, `cmp`, `SEO_id`), URL-decode percent-encoded path, remove trailing slash, keep at most the first 2 path segments for matching while preserving the original in `website_raw`. |

**Derived columns added at this stage**
- `geohash7` from valid lat/lng (≈150m cell, used as dedup blocking key)
- `name_core` (lowercase, accent-stripped, no punctuation, no leading article)
- `state_code`, `postal_code`
- `_quality_flags: List[Utf8]` — running list of issues per row

**Output**: `output/<run_id>/02_clean.parquet`, validated against `CleanRestaurant` Patito schema (typed, with constrained string sets where applicable).

**Tests**
- Property tests (hypothesis) for URL canonicalizer: idempotent, never raises on arbitrary input.
- Table-driven unit tests for each transform with known dirty inputs from the actual CSV (Traif/traif casing, `"Washington, DC"` quoting, `budget`/`unknown` price points, malformed place_ids).

**Risks / mitigations**
- *Over-aggressive name normalization breaks dedup of intentionally distinct venues* (e.g., `Carbone` vs `Carbone Vino Dallas`): keep `name` original, only use `name_core` for blocking/matching, and require geo + place_id co-signals before merging (Step 3).
- *Place_id false negatives*: log sample of rejected place_ids in run report so a human can spot-check.

## Step 3 — Deduplicate (Stage 3)

**Goal**: Resolve duplicates with explicit, tunable rules, merge complementary fields, and emit a record with provenance.

**Strategy: 3-tier match, single merge**

1. **Tier A — exact `google_place_id` match** (highest confidence, ~95% of detectable duplicates given the data).
   - Group by non-null cleaned `google_place_id`. Rows in same group → duplicates. Confidence = 1.0.
2. **Tier B — geo + name match** (catches cases where one duplicate has a fabricated/null place_id).
   - Block by `geohash6` (~1.2km) ∩ same `city_canonical`.
   - Within block, compute pairwise `rapidfuzz.token_set_ratio(name_core_a, name_core_b)`.
   - Match if ratio ≥ **92** AND haversine distance ≤ **150m** AND (same `state_code` OR one is null).
   - Confidence = 0.85 + (ratio − 92) × 0.01.
3. **Tier C — website match** (catches cross-location chain confusion in reverse: same website + same city = same venue when geo is missing).
   - Block by canonical `website` host+first-path-segment. Match within same `city_canonical`. Confidence = 0.80.
   - This tier is **disabled by default** (configurable) because chains like Uchi, Carbone, Le Jardinier have legitimate same-website different-locations rows. Enabled only when geo is null on both sides.

Configurable thresholds live in `configs/local.yaml` under `dedup:`.

**Cluster building**
- Treat matches as edges; compute connected components with `networkx` (small graphs, fine).
- Each component is one canonical venue.

**Merge rules** (per cluster, implemented in `src/revel/dedup.py:merge_cluster`)
- For each field, pick the value with the highest priority:
  1. Non-null wins over null.
  2. Most specific wins (longer `display_address`; address with state+zip > without).
  3. For `price_point`, keep the **mode**; ties broken by `high > medium > low`.
  4. For `primary_type`, keep most specific (e.g., `italian_restaurant` over `restaurant`).
  5. For `website`, prefer the canonicalized form; keep the longest `website_raw`.
  6. For `latitude`/`longitude`, take the median of valid values in the cluster (resilient to one bad pin).
- Add provenance columns:
  - `source_ids: List[Int64]` — every original `id` in the cluster
  - `dedup_confidence: Float64` — min confidence of any merge edge in the cluster
  - `dedup_tier: Utf8` — `A`, `B`, `C`, or `singleton`
  - Carry forward `_quality_flags` (union)

**Output**: `output/<run_id>/03_dedup.parquet` + `output/<run_id>/03_dedup_report.json`:
- counts per tier, cluster size histogram, top-N largest clusters with names for human review, edge cases (Tier C activations, geo-only matches with low ratio).

**Tests**
- Unit tests with synthetic clusters covering each tier + the merge precedence rules.
- A regression fixture using known dupes from the real CSV (Traif/traif, Dirt Candy x2, Ivan Ramen x3, Merois/The Merois, Antoine's Restaurant/Restaurnt, dLeña casing variants) — assert they collapse to exactly N canonical rows.

**Judgment calls (documented in `docs/dedup-judgment.md`)**
- Hotels are kept distinct from their in-house restaurants even when they share an address (different `primary_type` and `name_core`).
- Pop-ups inside another venue (e.g., `Colibrí Pop-up at Los Balcones`) are **not** merged with the host venue: distinct `name_core`.
- Same place_id appearing in different cities → treated as a data error; cluster is split by `city_canonical` and a flag is added.

**Risks / mitigations**
- *Over-merging chains*: Tier C off by default; require name match for Tier B even when geo matches.
- *Under-merging due to bad place_ids*: Tier B catches it; report surfaces clusters where Tier B was decisive for human spot-check on first runs.

## Step 4 — Fill & enrich with LLM agents (Stage 4)

**Goal**: Populate missing values, classify cuisine, and score romantic date suitability. All LLM use is cached, batched, and bypassable via `--dry-run`.

**Sub-step 4a — Deterministic fills first** (no LLM)
- Missing `city`: reverse-geocode lat/lng with `reverse_geocoder` (offline DB). Map to `city_canonical` via the same YAML used in Step 2.
- Missing `state_code` / `postal_code`: re-extract from `display_address` if it was filled by another row in the cluster post-merge.
- Missing `latitude`/`longitude`: leave null (no third-party API by default; flag for follow-up).

**Sub-step 4b — Cuisine classification** (`src/revel/agents/cuisine.py`)
- **Stage 1: rule-based** mapping from `primary_type` → cuisine, defined in `configs/cuisine_taxonomy.yaml`. Covers ~85% of rows deterministically:
  - `italian_restaurant` → `Italian`, `french_restaurant`/`modern_french_restaurant` → `French`, `japanese_restaurant`/`sushi_restaurant`/`ramen_restaurant`/`izakaya_restaurant`/`kaiseki_restaurant` → `Japanese`, `chinese_restaurant`/`cantonese_restaurant` → `Chinese`, `mexican_restaurant`/`oaxacan_restaurant`/`taqueria` → `Mexican`, `korean_restaurant`/`korean_barbecue_restaurant` → `Korean`, `mediterranean_restaurant`/`greek_restaurant`/`israeli_restaurant`/`middle_eastern_restaurant`/`spanish_restaurant`/`portuguese_restaurant` → `Mediterranean`, `american_restaurant`/`new_american_restaurant`/`southern_restaurant`/`barbecue_restaurant`/`creole_restaurant`/`cajun_restaurant`/`californian_restaurant`/`pacific_northwest_restaurant` → `American`, `vietnamese_restaurant`/`thai_restaurant`/`southeast_asian_restaurant`/`filipino_restaurant`/`laotian_restaurant`/`cambodian_restaurant`/`indonesian_restaurant` → `Southeast Asian`, `indian_restaurant`/`modern_indian_restaurant` → `Indian`, `peruvian_restaurant`/`argentinian_restaurant`/`south_american_restaurant`/`panlatin_restaurant`/`latin_american_restaurant` → `Latin American`, `west_african_restaurant`/`ethiopian_restaurant`/`african_restaurant` → `African`, `seafood_restaurant`/`oyster_bar_restaurant` → `Seafood`, `steak_house` → `Steakhouse`, `pizza_restaurant` → `Pizza`, `vegetarian_restaurant`/`vegan_restaurant` → `Vegetarian/Vegan`, `asian_fusion_restaurant`/`asian_restaurant` → `Asian (Fusion)`, `fine_dining_restaurant`/`bistro` → `null` (escalate to LLM), `restaurant`/`hotel`/`bar`/`cafe` → `null` (escalate).
  - Output column: `cuisine` (single value from a closed taxonomy of ~20 categories), plus `cuisine_secondary` (optional).
- **Stage 2: LLM fallback** for nulls from Stage 1. Single batched prompt per N=20 rows. Inputs: `name`, `name_core`, `primary_type`, `website` host, `city`, `display_address`. Output: structured JSON `{cuisine, cuisine_secondary, confidence}` validated against the same taxonomy. Confidence below 0.6 → leave null + flag.

**Sub-step 4c — Romantic date suitability scoring** (`src/revel/agents/romance.py`)
- **Multi-dimensional rubric** (documented in `docs/romance-scoring.md`):
  - `ambiance` (0-10): from `primary_type` (fine_dining, wine_bar, cocktail_bar, italian, french → high; diner, fast food, sandwich_shop → low) + `price_point` (high → +2).
  - `intimacy` (0-10): heuristic from cuisine + `name`/`name_core` cues (e.g., "omakase", "tasting", "chef's table" → high; "grill", "bar", "club", "tavern" → lower-mid).
  - `quietness` (0-10): inverse of party-vibe signals in `name`/`primary_type` (`night_club`, `live_music_venue`, `gay_bar` → low; `fine_dining`, `kaiseki` → high).
  - `dining_experience` (0-10): `price_point` (high → 8-10, medium → 5-7, low → 2-4) + cuisine prestige bump.
  - `cuisine_fit` (0-10): cuisines with strong romantic associations (French, Italian, Japanese omakase, Mediterranean) → high; barbecue, diner, fast-casual → low.
- **Composite score**: weighted sum, weights configurable in `configs/local.yaml`:
  - Default: `0.25 ambiance + 0.20 intimacy + 0.15 quietness + 0.20 dining_experience + 0.20 cuisine_fit`, scaled to 0-100.
- **Computation path**:
  - For rows with high-signal `primary_type` + `price_point` non-null: deterministic score from a lookup table.
  - For rows with weak signals (e.g., `primary_type=restaurant`, null price): batch LLM call returning the 5 sub-scores + 1-2 sentence `romance_rationale`. Validated with Pydantic; out-of-range scores → reject + retry once → fall back to deterministic with flag.
- **Output columns**: `romance_score: Int8` (0-100), `romance_subscores: Struct{ambiance, intimacy, quietness, dining_experience, cuisine_fit}`, `romance_rationale: Utf8`.

**LLM client contract** (`src/revel/llm/client.py`)
- Provider-agnostic protocol: `complete_json(messages, schema, max_retries=2) -> dict`.
- `diskcache` keyed on `sha256(provider + model + messages + schema_version)` so reruns cost zero.
- Concurrency via `asyncio.Semaphore` set to `llm_max_concurrency`.
- Structured logs: only count of tokens and cache hits — **never log prompt content** (it contains business data). Log redaction enforced by `logging_setup.py`.
- `--dry-run` mode injects deterministic stubs so tests and CI never call out.

**Output**: `output/<run_id>/04_enriched.parquet` + `04_enrichment_report.json` (cuisine distribution, LLM fallback rate, score histogram).

**Tests**
- Cuisine: every `primary_type` in the input maps to either a deterministic cuisine or to "escalate" — pinned via a parameterized test.
- Romance: golden-file test on 20 representative rows; assert score deltas stay within tolerance when sub-score weights change predictably.
- Stub LLM client used in CI; live calls only behind an env flag.

**Risks / mitigations**
- *LLM hallucinated cuisines outside taxonomy*: enforce closed-set with Pydantic `Literal[...]`; on violation, retry once, then null + flag.
- *Cost blowup*: cache + batching + `dry_run`; report estimated cost in run summary before live calls (configurable confirmation prompt for >$X).
- *Subjectivity of romance score*: rubric is documented, weights are configurable, sub-scores and rationale are kept so downstream consumers can re-weight.

## Step 5 — Validate, publish, notify (Stages 5-7)

**Goal**: Hard schema/integrity checks, partitioned Parquet output, and a single human-readable run report.

**Validation** (`src/revel/validate.py`)
- Patito `PublishedRestaurant` model enforces:
  - `id: Int64` (renamed `canonical_id`, generated as `min(source_ids)` for stability across reruns; original ids preserved in `source_ids`).
  - `name: Utf8 != ""`.
  - `city_canonical ∈` closed set from `configs/cities.yaml`.
  - `latitude ∈ [17, 72]`, `longitude ∈ [-180, -65]` OR both null.
  - `price_point ∈ {low, medium, high, null}`.
  - `cuisine ∈` closed taxonomy OR null.
  - `romance_score ∈ [0, 100]`.
  - `google_place_id` matches the validated regex OR null.
  - `source_ids` non-empty, uniqueness of `canonical_id` across the frame.
- Cross-row checks:
  - No duplicate `google_place_id` after dedup (assert; failure aborts publish).
  - Every row has at least one of (`google_place_id`, `(latitude, longitude)`, `display_address`).
  - `cuisine` null rate ≤ configurable threshold (default 5%); above → warning, not error.
- Failures collected into a single `ValidationReport` and surfaced in logs + report; **abort publish on any error-level violation** (fail-closed per security rules).

**Publishing**
- Write `output/<run_id>/restaurants.parquet` with:
  - `compression="zstd"`, `compression_level=3`
  - Row group size 50k (small dataset, but sets pattern for scaling)
  - Column metadata embedding: `pipeline_version`, `git_sha`, `run_id`, `source_csv_sha256`, `cuisine_taxonomy_version`, `dedup_thresholds_used`
- Also write `output/<run_id>/restaurants.csv` (utf-8, no index) for non-Parquet consumers; keep this gated behind a `--also-csv` flag.
- Atomic publish: write to `.../_tmp/`, then rename. Update `output/latest` symlink only on success.

**Run report** (`output/<run_id>/run_report.md`)
- Inputs: source path + sha256, row count.
- Per-stage counts, drops, and flag tallies.
- Dedup tier breakdown + top 20 largest clusters with member names.
- Cuisine distribution (deterministic vs LLM-resolved).
- Romance score histogram + top/bottom 10.
- LLM usage: cache hit rate, total tokens, estimated cost.
- Validation summary (errors, warnings).
- Wall-clock per stage, peak memory.

**Notify**
- Default: write `run_report.md` and emit one structured INFO log line summarizing status + path.
- Pluggable hook (`src/revel/notify.py`) with implementations: `console` (default), `file` (writes to a configured path), `webhook` (POSTs JSON to a URL from env var). Webhook is opt-in via config; off by default. Never include raw row data in notifications, only counts and the report path.

**CLI surface (final)**
```
just pipeline run --input input/restaurants.csv --output output/ [--dry-run] [--also-csv] [--config configs/local.yaml]
just pipeline validate --parquet output/latest/restaurants.parquet
just pipeline report --run-id <id>
just lint
just typecheck
just test
just check    # lint + typecheck + test
```

**Tests**
- End-to-end test: full pipeline on the 20-row fixture in `--dry-run` mode produces a valid parquet + report; second run produces byte-identical parquet (idempotency check via sha256 of sorted rows + metadata excluded).
- Validation test: inject a row that violates each constraint; assert the publish step aborts with a useful error.

**Quality gates before merge**
- All MUST/SHOULD items in `workflow-and-quality.md` for Large changes:
  - ruff, mypy --strict, pytest, integration test all pass
  - `docs/` updated (`dedup-judgment.md`, `romance-scoring.md`, `cuisine-taxonomy.md`)
  - PR description with summary, what was tested, judgment calls, known limitations
  - `TECHNICAL_DEBT.md` for deferred items (third-party geocoding, schema evolution policy, observability metrics export)

**Risks / mitigations**
- *Schema drift on future inputs*: `RawRestaurant` Patito model fails fast on missing/extra columns; new columns require a code change + schema bump (documented in `docs/schema-evolution.md`).
- *Non-determinism from LLM*: caching makes reruns deterministic; `temperature=0`; structured outputs enforced.
- *Atomic publish failure mid-write*: write to `_tmp/` first, rename last; old `output/latest` untouched until rename succeeds.

## Open questions to confirm before Step 4

These are the only blocking items; everything above is implementable as-is.

1. **LLM provider + budget**: OpenAI default? Hard cap (e.g., $5 per run)? An answer here decides whether we add a confirmation prompt.
2. **Whether to call Google Places API** for missing addresses/coords. Default plan: **no** (offline only) to keep the pipeline self-contained and free. Confirm or unblock with an API key.
3. **Cuisine taxonomy granularity**: ~20 categories proposed. Need finer (e.g., split `Japanese` into `Sushi/Omakase` vs `Izakaya/Ramen`) or coarser?

Defaults above are usable without resolving these; flag for review at Step 4 kickoff.
