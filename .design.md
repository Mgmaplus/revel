# Restaurant Pipeline — Design Plan (v1)

> **Purpose**: Lock the architectural decisions before any code is written. This doc complements `.plan.md` (implementation plan). Where the two disagree, this design wins and `.plan.md` will be revised at the bottom of this file.
>
> **Scope of this version**: v1 — local, single-machine, manual CLI trigger, ~1k rows. Designed so v2/v3 are additive, not rewrites.

---

## 1. Design goals

1. **Deterministic by default, LLM only where it must be.** Every transform that can be expressed in SQL or pure Python is. LLMs are reserved for fields that genuinely require fuzzy reasoning (cuisine when the Google Places type is generic, romance scoring rubric).
2. **Validated handoffs between stages.** No stage trusts the previous one — each boundary has an enforced schema and a set of tests that fail the run if data integrity is violated.
3. **Replicable on any CSV that matches the input contract.** No row-specific code paths; everything driven by config and reference seeds.
4. **Forward-compatible.** v1 is the smallest pipeline that does the job correctly. Migrations to Dagster (orchestration), LangGraph (agent reasoning), and a warehouse (storage) are pre-planned but not implemented.

## 2. Non-goals for v1

- Real-time / streaming ingestion.
- Multi-tenant or multi-input concurrency.
- Web scraping or third-party API calls (Google Places, Yelp). All enrichment is offline + LLM.
- Schema-evolution machinery beyond a version pin.
- A UI.

### ADR-001 — Staging layer: dbt-core + dbt-duckdb (Parquet-backed)

**Decision**: All deterministic stages (Ingest, Clean, Deduplicate, deterministic parts of Fill) run as **dbt models against DuckDB**, materializing Parquet files on disk. Python orchestrates dbt as a subprocess and consumes the final pre-agent Parquet.

**Why this over Polars-only**:
- dbt gives us **schema tests, not_null/unique/accepted_values/relationships, and column-level docs for free**. Hand-rolling these in Python is reinventing dbt poorly.
- DuckDB reads CSV and writes Parquet natively, has zero-copy interop with Polars (`duckdb.sql(...).pl()`), and runs in-process — no service to manage.
- SQL is the right language for filter/group/window/dedup. A dedup tier defined as a window function is more readable and reviewable than equivalent Polars chains.
- dbt's lineage graph is genuine project documentation; we get it for free.
- Sets up v2 (Dagster software-defined assets) cleanly: each dbt model becomes a Dagster asset via `dagster-dbt`.

**Why not pure Polars**:
- Tests, lineage, and docs would all be hand-rolled.
- Migration to a warehouse later (Snowflake/BigQuery) requires re-writing transforms; with dbt, you swap the adapter.

**Why not a managed warehouse for v1**:
- 1000 rows, single laptop. DuckDB is faster and free. Same dbt code targets a real warehouse on day one of v2 if needed.

**Layer plan** (final names; see §4 for materialization details):
```
seeds/
  cuisine_taxonomy.csv          -- primary_type → cuisine, deterministic mapping
  city_canonical.csv            -- raw city → canonical city + state
  price_point_mapping.csv       -- raw → {low, medium, high, null}
  place_id_prefixes.csv         -- valid Google place_id prefixes

models/
  sources.yml                   -- declares input CSV as a dbt source
  raw/
    raw_restaurants.sql         -- typed pull from source CSV, no transforms
  staging/
    stg_restaurants.sql         -- per-column cleaning (string ops, regex, casts)
    stg_restaurants__flagged.sql -- adds _quality_flags struct
  intermediate/
    int_restaurants__deduped.sql -- 3-tier dedup with window functions, merge logic
    int_restaurants__enriched_det.sql -- deterministic cuisine + reverse-geocode fills
  marts/
    dim_restaurants__pre_agent.sql -- final handoff table to Python (Parquet, external)
```

**Materialization strategy**:
- `raw/` and `staging/` → `view` (cheap, recomputed each run, easy to debug).
- `intermediate/` → `table` (persisted in DuckDB for re-runs and tests).
- `marts/dim_restaurants__pre_agent` → **`external`** (Parquet on disk) so Python reads it natively without going through DuckDB.

**Tests v1** (live in `models/*/schema.yml`):
- `raw_restaurants`: column presence, types.
- `stg_restaurants`: `not_null` on `id`, `name`; `accepted_values` for `price_point ∈ {low, medium, high, null}`; `dbt_utils.expression_is_true` for lat/lon ranges.
- `int_restaurants__deduped`: `unique` on `canonical_id`; `unique` on `google_place_id` where not null.
- `dim_restaurants__pre_agent`: row count within ±5% of input minus expected dedup collapse.

**Tests v2 (deferred)**: source freshness, snapshots, custom singular tests for cluster sanity, dbt-expectations.

**Migration path forward**:
- v2: `dagster-dbt` wraps every model as a Dagster asset; orchestration moves from `subprocess.run(["dbt", "run"])` to `dagster job execute`.
- v3 (if scale demands): swap `profiles.yml` adapter from `duckdb` to `snowflake`/`bigquery`. Models are 95% portable; DuckDB-specific functions (e.g., `regexp_extract_all`) get small rewrites.

**Reversibility**: Single-file rewrite to Polars if dbt proves to be friction. Estimated cost: ~2 days. Likelihood: low.

### ADR-002 — Agent layer: deterministic + structured-output LLM (Gemini), **no agent framework** for v1

**Decision**: The Fill & Transform stage is a Python module of plain async functions. LLM calls go through a thin `LLMClient` interface that returns Pydantic-validated structured output. **No LangGraph, no LangChain, no agents-style routing in v1.**

**Why this over LangGraph**:
- LangGraph earns its complexity when the workload has branching reasoning, tool use, or multi-turn state. Ours has none of those: each row is processed once, with at most one LLM call per concern (cuisine, romance), with structured input and structured output.
- LangGraph adds: a state graph, checkpointers, persistence layer, and a debug surface we don't need. Cost is real (extra deps, harder testing, slower iteration on prompts).
- The deterministic majority of the work (~85% of cuisine, all of reverse-geocoding city fills, most romance scoring via rubric) is plain table joins and Python — wrong shape for a graph orchestrator.

**Why not pure agent**:
- An LLM cannot deterministically maintain a closed taxonomy across 1000 rows. We'd be pre-validating + post-validating the agent anyway, which is what we're already doing without the agent harness.
- Cost and latency: a single batched call covering 20 rows is ~50× cheaper than per-row agent runs.

**v1 design**:
```
src/revel/enrich/
  __init__.py
  cuisine.py         -- classify_cuisine(rows) -> rows; rule-based first, LLM fallback
  romance.py         -- score_romance(rows) -> rows; rubric first, LLM for ambiguous
  fills.py           -- fill_missing(rows) -> rows; reverse_geocode, address re-derive
  llm/
    client.py        -- LLMClient protocol; GeminiClient impl; StubClient impl for tests
    cache.py         -- diskcache wrapper, key = sha256(provider+model+prompt+schema)
    schemas.py       -- Pydantic models for structured outputs
```

Each function:
1. Reads a Polars DataFrame from the dbt mart.
2. Splits rows into `deterministic_path` and `llm_path` based on signal availability.
3. Processes both paths.
4. Concatenates and returns.
5. Logs counts per path; never logs row contents (security).

LLM calls:
- **Provider**: Google Gemini via `google-genai` SDK, model `gemini-2.0-flash`. `temperature=0`, `response_mime_type="application/json"`, `response_schema=<Pydantic>` so the model is forced to a Pydantic-compatible shape.
- Batched at 20 rows per request to amortize overhead.
- Concurrency via `asyncio.Semaphore` (default 4).
- Cached by content hash (diskcache) to make reruns free and deterministic.
- `--dry-run` injects `StubClient` that returns canned outputs; CI uses it; tests use it. `GEMINI_API_KEY` only required for live runs.

**Provider portability**: Behind the `LLMClient` protocol, OpenAI / Anthropic / local Ollama can be swapped without touching enrichment code. Provider chosen via `LLM_PROVIDER` env var; secrets only in `.env`.

**Migration path forward**:
- v2 (if multi-step reasoning emerges, e.g., "infer cuisine by reading the website"): each function becomes a LangGraph node, the rows-DataFrame becomes the graph state. Function signatures stay close enough that the rewrite is mechanical.
- v3 (if we want true agency, e.g., dynamic tool selection): full LangGraph with tools. Still a refactor, not a rewrite, because the LLM client and Pydantic schemas carry over.

**Reversibility**: High. The whole layer is ~3 modules of plain functions; replacing them with LangGraph is bounded work.

### ADR-003 — Versioning roadmap

**Decision**: Pipeline is explicitly versioned. v1 ships now with a documented set of deferred items. Each future version is additive — earlier code keeps working unchanged.

| Concern | v1 (now) | v2 (next) | v3+ (if needed) |
|---|---|---|---|
| Trigger | Python CLI (`typer`) via `just` | Dagster scheduled/sensor-driven job | API endpoint + event trigger |
| Orchestration | Python script calling dbt subprocess + enrichment functions | `dagster-dbt` software-defined assets, full asset graph | Same, but multi-tenant |
| Staging | dbt-duckdb, 1 mart, basic schema tests | Full test suite (`dbt-expectations`, source freshness, snapshots) | Warehouse adapter (Snowflake/BigQuery) |
| Agent layer | Deterministic + structured-output LLM, no framework | Same, unless multi-step reasoning needed | LangGraph nodes, tool use |
| Storage | Local Parquet, atomic rename | Versioned via Dagster IO managers, partitioned by `run_id` | Warehouse tables + Parquet exports |
| Validation | Patito at boundaries + dbt tests | Add cross-stage Great Expectations suites; threshold-based alerts | SLAs, data contracts |
| Notification | Console + `run_report.md` | Slack/webhook on threshold violations + Dagster sensors | PagerDuty for hard SLA breaches |
| Observability | structlog JSON logs | Dagster runtime metrics, OpenTelemetry traces | Full APM |
| Cost control | diskcache + per-run cost summary | Per-asset cost budgets, alerting | Programmatic cost limits |

**Versioning mechanics**:
- `pipeline_version` constant in `src/revel/__init__.py`. Embedded in Parquet metadata and `run_report.md`. Bumped on any change to output schema or transform semantics.
- Output schema versions tracked in `docs/schema-versions.md`. Breaking changes require a version bump and a migration note.
- Each ADR above becomes a real file in `docs/adr/` once implemented (`0001-staging-with-dbt.md`, etc.). New decisions add new ADRs; superseded ADRs are marked "Superseded by ADR-NNN" but kept.

### ADR-004 — Local-only execution + DuckDB-as-storage in v1

**Decision**: The entire pipeline runs end-to-end on a single developer laptop, with **no managed services**. Storage between dbt models is the embedded DuckDB file `data/revel.duckdb`. External Parquet is used **only at three boundaries**: input handoff (CSV → DuckDB), pre-agent handoff (DuckDB → Polars), and final publish (Parquet to consumers).

**Why this matters**:
- dbt-duckdb does **not** require a database server. DuckDB is an in-process embedded engine; the "warehouse" here is a single file. There is no Postgres, no Snowflake, no cloud storage, no Docker, no Airflow in v1.
- This was an open question implicitly raised when we discussed materialization. Locking it: **per-stage Parquet snapshots are not used**. The `02_clean.parquet` and `03_dedup.parquet` artifacts that appeared in early drafts are removed. Intermediate state lives inside `data/revel.duckdb` and is queryable directly: `duckdb data/revel.duckdb -c "SELECT * FROM main.stg_restaurants__flagged LIMIT 20"`.
- Per-stage **JSON stats** (counts, flag tallies) are still written to `output/<run_id>/0N_*.json` for the run report — small, human-readable, no Parquet overhead.

**External network calls in v1**: exactly one — Gemini API (`generativelanguage.googleapis.com`). All other operations are local file I/O.

**Materialization rules** (final for v1):
- `raw_restaurants`, `stg_restaurants*` → **`view`** (no physical bytes; recomputed each run)
- `int_restaurants__deduped`, `int_restaurants__enriched_det` → **`table`** (lives inside `data/revel.duckdb`; survives across runs for debugging)
- `dim_restaurants__pre_agent` → **`external`** Parquet at `data/pre_agent/restaurants.parquet` (Python reads via `pl.read_parquet` without holding a DuckDB connection)
- Final published artifact → Parquet at `output/<run_id>/restaurants.parquet`

**Required for the "works locally" guarantee**:
- `.env` with `GEMINI_API_KEY` (or `--dry-run` to bypass LLM entirely)
- `uv sync` installs all deps including `dbt-duckdb`
- `just pipeline run` performs every stage without any service running
- Tests + CI run with `--dry-run` and need no API key

**Migration paths**:
- v2: same DuckDB file behind Dagster IO managers; no transform changes needed.
- v3: switch dbt adapter to a real warehouse (Snowflake/BigQuery); the `external` Parquet boundary stays as the Python handoff.

**Reversibility**: Trivially. Any of the three Parquet boundaries can be replaced with a different format (e.g., Arrow IPC) without touching transforms.

## 5. Stage-by-stage decisions (v1-only details)

### 5.1 Ingest (dbt source)
- Source CSV declared in `models/sources.yml` with `external_location` pointing to `input/restaurants.csv`.
- `raw_restaurants.sql` does `SELECT * FROM {{ source('raw', 'restaurants') }}` with explicit casts.
- dbt source-level tests: column presence (built-in), row count > 0.

### 5.2 Clean (dbt staging)
- All transforms from `.plan.md` Step 2 expressed as SQL using DuckDB string functions and `regexp_extract`.
- The URL canonicalizer is the only transform that's awkward in pure SQL; implemented as a **dbt macro** (`{{ canonicalize_url(col) }}`) wrapping a chain of `regexp_replace` calls. If this gets ugly, downgrade it to a Python UDF via dbt-duckdb's `python_function` feature — kept as a fallback, not a goal.
- `_quality_flags` modeled as a `LIST(VARCHAR)` column, built up via `array_concat` of conditional flag literals.

### 5.3 Dedup (dbt intermediate)
- 3-tier match logic implemented as three CTE blocks in `int_restaurants__deduped.sql`.
- Connected components on match edges: DuckDB doesn't have native graph support, so for v1 we use the **union-find approximation via iterative SQL** OR — cleaner — call out to a small Python step that reads the edge list, runs `networkx.connected_components`, and writes back a `cluster_id` table that `int_restaurants__deduped` joins against.
- **Decision**: take the Python step. It's 30 lines, deterministic, easy to test. The cluster_id table is a dbt **seed-like artifact** written by Python before the intermediate model runs. Documented as the only "code-side" piece in the otherwise-SQL pipeline; flagged for v2 reconsideration if dbt or DuckDB grows graph primitives.
- Merge rules from `.plan.md` Step 3 expressed as `array_agg` + `arg_max` + custom precedence in SQL.

### 5.4 Deterministic enrichment (dbt intermediate)
- Cuisine via join against `seeds/cuisine_taxonomy.csv`. Rows where the join nulls → flagged for LLM.
- City fill via reverse-geocode: precomputed once into `seeds/cities_by_geohash5.csv` (offline using `reverse_geocoder`), joined in SQL. No runtime Python lookup.

### 5.5 Pre-agent mart (dbt mart, external Parquet)
- `dim_restaurants__pre_agent.sql` selects the final columns + `_needs_llm_cuisine` and `_needs_llm_romance` boolean flags.
- Materialized as `external` Parquet at `data/pre_agent/restaurants.parquet`.

### 5.6 Agent enrichment (Python)
- Reads pre_agent Parquet via Polars.
- Splits into deterministic and LLM paths per `_needs_llm_*` flags.
- LLM batched, cached, structured-output. Closed taxonomies enforced.
- Writes `data/enriched/restaurants.parquet`.

### 5.7 Validate, publish, notify
- Patito validates the enriched frame against the published schema.
- Atomic write to `output/<run_id>/restaurants.parquet`, then update `output/latest` symlink.
- `run_report.md` generated. Console log emits status + path.

## 8. Open items that still need a human decision

Same three as before, deferred to Step 4 kickoff:

1. **Gemini per-run cost cap.** Default proposal: hard cap $2/run with confirmation prompt above that.
2. **Should we ever call Google Places** for missing addresses/coords? Default: **no** (would break the local-only guarantee per ADR-004).

None of these block Steps 1-3.

## 9. Risks introduced by this design

| Risk | Likelihood | Mitigation |
|---|---|---|
| dbt-duckdb adapter has a bug on a transform we depend on | Low | Use stable 1.7+; complex transforms (URL canonicalize) have a Python-UDF fallback path. |
| URL canonicalization is too painful in SQL | Medium | Pre-decided fallback: dbt-duckdb python_function. Cost: ~1 hour to switch. |
| Connected-components-in-Python step feels out of place | Low | Documented as a known v1 wart; revisit in v2 with `dagster-dbt` where it can be its own asset. |
| LLM provider lock-in via Gemini structured outputs | Low | `LLMClient` protocol abstracts it; OpenAI / Anthropic / local Ollama swap without touching enrichment code. |
| Patito vs dbt tests overlap | Low | Patito tests the Python-side post-agent frame; dbt tests the pre-agent SQL frame. No overlap by construction. |
