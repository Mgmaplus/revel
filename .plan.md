# Restaurant CSV → Production Dataset: Implementation Plan (v1)

> **Scope**: Replicable, idempotent pipeline for `input/restaurants.csv` and any future CSV with the same schema. Stages from `project-overview.md`: Ingest → Clean → Deduplicate → Fill & Transform → Validate → Publish → Notify.
>
> **Architectural baseline** (locked in `.kiro/steering/architecture-decisions.md`):
> - Stages 1–3 + deterministic part of Stage 4 ⇒ **dbt-core + dbt-duckdb** (ADR-001)
> - Stage 4 LLM portion ⇒ **plain Python + Gemini structured outputs**, no agent framework (ADR-002)
> - v1 trigger is a **Python CLI**; v2 wraps with Dagster (ADR-003)
> - **Local-only execution**: no DB server, no cloud, single embedded DuckDB file (ADR-004)
>
> **Effort sizing**: Large (>500 lines, multi-module). Apply full quality gate per `workflow-and-quality.md`.
>
> **Tech stack** (decided): Python 3.12, uv, just, dbt-core + dbt-duckdb, Polars, Pydantic v2, Patito, `google-genai` SDK (Gemini), diskcache, structlog, typer, ruff, mypy, pytest, hypothesis, rapidfuzz, unidecode, networkx, pygeohash, reverse_geocoder.
>
> **Storage layout** (per ADR-004):
> - `input/restaurants.csv` — source
> - `data/revel.duckdb` — embedded DB; raw/staging/intermediate models live here as views/tables
> - `data/pre_agent/restaurants.parquet` — sole intermediate Parquet (handoff to Python enrichment)
> - `output/<run_id>/restaurants.parquet` — final published artifact
> - `.cache/` — diskcache for LLM responses
>
> **External network calls in v1**: exactly one — Gemini API. Tests + CI run with `--dry-run` and need no API key.

## Step 1 — Project scaffold, config, dbt source + raw model (Stage 1)

> **Status: ✅ Implemented.** Run `just check` and `just pipeline-run` to verify locally. End-to-end smoke test in `tests/integration/test_pipeline_step1.py`.
>
> **Implementation notes for the next dev** (lessons from actually building this):
>
> - **dbt-duckdb source CSV reads.** The `external.options` block in `sources.yml` is a *no-op* on dbt-duckdb 1.9 — dbt only honors `meta.external_location`. To pin CSV read parameters, wrap the path in a `read_csv(...)` call inside `external_location` (see `dbt/models/sources.yml`). Without this, DuckDB's auto-detection silently treats the literal string `"null"` as a value rather than NULL, and our null-detection stats are wrong by orders of magnitude.
> - **Source-level tests don't fire on `--select <model>`.** dbt only runs `not_null`/`unique` declared on a source if you select `source:raw` explicitly. The orchestrator does this: `dbt build --select source:raw raw_restaurants`. Drop the `source:raw` and you lose the input-validation gate.
> - **`DBT_PROFILES_DIR`.** dbt looks in `~/.dbt/profiles.yml` by default, which is wrong for a self-contained repo. The orchestrator sets `DBT_PROFILES_DIR` to the dbt project dir and `just dbt` does the same. If you ever invoke dbt by hand from outside `just`, set this env var or dbt will fail with "Path '/Users/.../.dbt' does not exist".
> - **`numeric` casts.** Use `TRY_CAST` on `latitude`/`longitude` so a single malformed numeric doesn't abort the whole build. We deliberately use plain `CAST` on `id` so a non-integer id *does* abort — that's a contract violation, not a row-level data quality issue.
> - **Config precedence.** Pydantic-settings treats kwargs as the *highest* priority source by default. `Settings.from_yaml()` works around this by dropping any YAML keys whose corresponding env var is set, so the documented precedence (YAML < env < CLI) actually holds. There is a unit test pinning this behavior; if you change `from_yaml`, run `tests/unit/test_config.py`.
> - **Typer ≥ 0.15.** Earlier versions crashed on `Optional[Path]` annotations when generating help. Don't downgrade.
> - **Real dataset stats** (1073 rows): `display_address` null in 108 rows, `price_point` null in 206 (~19%), `google_place_id` null in 5, `primary_type` has 102 distinct values. Step 4's deterministic cuisine taxonomy will need to cover that range.
> - **Where to look:**
>   - Orchestrator: `pipelines/restaurant_pipeline.py` (`run_pipeline` is the single entry point; later stages plug in here)
>   - Stage-1 stats: `src/revel/ingest.py`
>   - dbt project: `dbt/`
>   - Run artifacts: `output/<run_id>/01_ingest_stats.json`
>   - DuckDB warehouse: `data/revel.duckdb` (queryable directly: `duckdb data/revel.duckdb -c "SELECT * FROM raw_restaurants LIMIT 5"`)

**Goal**: A runnable `just pipeline run --input <csv>` that wires up Python + dbt, runs `dbt build --select raw_restaurants`, and validates the CSV against source-level tests. No row-level transforms yet.

**Deliverables**
- Repo layout exactly as in `project-overview.md` §4. Concretely:
  - `pyproject.toml` (uv-managed); `justfile`; `.env.example` with `GEMINI_API_KEY=` placeholder; `.gitignore` (excludes `.env`, `output/`, `data/`, `.cache/`, `dbt/target/`, `dbt/logs/`)
  - `dbt/dbt_project.yml`, `dbt/profiles.yml` (DuckDB target with path from env var `REVEL_DUCKDB_PATH`, default `data/revel.duckdb`)
  - `dbt/models/sources.yml` declaring the input CSV via `external_location` (DuckDB reads it directly with `read_csv_auto`)
  - `dbt/models/raw/raw_restaurants.sql` — `SELECT` with explicit casts; pinned read parameters: `header=true`, `nullstr=['', 'null', 'NULL', 'None']`, `all_varchar=true` then casts in SQL, `encoding='utf8'`
  - `src/revel/{__init__.py, cli.py, config.py, logging_setup.py, schemas.py}` — contracts + skeletons only
  - `pipelines/restaurant_pipeline.py` — orchestrator skeleton: `subprocess.run(["dbt", "build", ...])` wrapped in a function called by the CLI
  - `tests/{unit, dbt, integration}/` with one smoke test each
  - `tests/fixtures/restaurants_sample.csv` — 20 hand-picked rows from the real CSV that exercise every issue (place_id dups, missing addresses, unusual `price_point` values, fabricated place_ids)
  - `README.md` quickstart: `uv sync && cp .env.example .env && just pipeline run --dry-run`

**Source declaration + raw model**
- `sources.yml` declares the raw CSV with column-level descriptions and minimal source tests:
  - `not_null` on `id`, `name`
  - `unique` on `id`
  - `dbt_utils.expression_is_true` `count(*) > 0`
- `raw_restaurants.sql` materialized as **`view`** (no physical file). Casts: `id::BIGINT`, `latitude::DOUBLE`, `longitude::DOUBLE`, all others `VARCHAR`. Column order preserved.
- Per-stage stats logged to `output/<run_id>/01_ingest_stats.json` by a small Python step that runs `duckdb.connect(path).sql("SELECT ... FROM raw_restaurants").pl()` after `dbt build`. Stats include row count, null count per column, distinct count for `price_point` / `primary_type` / `city`.

**Config strategy**
- `Settings(BaseSettings)` loads `configs/local.yaml`, overlays `.env`, then CLI flags. Fields:
  - `input_path`, `output_dir`, `data_dir` (default `data/`), `duckdb_path` (default `data/revel.duckdb`)
  - `llm_provider` (default `gemini`), `llm_model` (default `gemini-2.0-flash`), `llm_max_concurrency` (default 4), `llm_cache_dir` (default `.cache/llm`)
  - `dedup_thresholds` (see Step 3), `cuisine_taxonomy_path`
  - `dry_run` (skip LLM calls; use `StubClient`), `also_csv` (publish CSV alongside Parquet)
- Secrets only via env (`GEMINI_API_KEY`); never in YAML or logs. Pydantic `SecretStr` fields auto-redacted.

**Quality gates for this step**
- `ruff check` + `ruff format --check`
- `mypy --strict` over `src/revel/` and `pipelines/`
- `dbt parse` succeeds
- `dbt build --select raw_restaurants` succeeds against the fixture CSV
- Unit test: malformed CSV (missing column) fails source-level test with a useful message
- Integration test: `just pipeline run --input tests/fixtures/restaurants_sample.csv --dry-run` exits 0 and writes `01_ingest_stats.json`

**Risks / mitigations**
- *DuckDB external CSV auto-detects schema and gets it wrong*: pin read parameters in `sources.yml`; explicitly cast in `raw_restaurants.sql`.
- *Cross-platform encoding*: force `encoding='utf8'`; fail with actionable error otherwise.
- *Embedded commas in `display_address`*: standard quoted-field handling; verified by sample row in fixture.

## Step 2 — Clean & normalize as dbt staging models (Stage 2)

> **Status: ✅ Implemented.** Run `just check` and `just pipeline-run` to verify locally. Unit tests for UDFs in `tests/unit/test_dbt_plugin.py`; end-to-end smoke test in `tests/integration/test_pipeline_step2.py`.
>
> **Implementation notes for the next dev** (lessons from actually building this):
>
> - **Pure-SQL URL canonicalization is a trap.** The plan flagged this as a risk; I went straight to the documented fallback (Python UDF via dbt-duckdb plugin) and saved hours. Don't attempt a `regexp_replace` chain — the percent-encoded URLs in the input (e.g., the Four Seasons row with `%3F...%26utm_*`) will defeat any pure-SQL approach. UDFs live in `src/revel/dbt_plugin.py`. **Three UDFs registered**: `clean_url`, `geohash`, `name_core` — all defensive (NULL → NULL, never raise).
> - **dbt-duckdb plugin discovery: a tiny gotcha.** The plugin module path in `dbt/profiles.yml` (`module: revel.dbt_plugin`) must be importable from dbt's Python process. Because we use `uv run dbt`, the `revel` package on `src/` is on PYTHONPATH automatically. If you ever run dbt outside `uv`, you'll need `pip install -e .` or the plugin won't be found.
> - **UDFs live in the connection, not the .duckdb file.** Views built with UDFs only resolve when the same UDFs are registered on the *reading* connection. That means anyone who connects to `data/revel.duckdb` with plain `duckdb` and queries `stg_restaurants` will get `Catalog Error: Scalar Function with name name_core does not exist`. The fix: `from revel.dbt_plugin import register_udfs; register_udfs(conn)` — see `src/revel/clean.py` for an example. The orchestrator's stats step does this. **The CLI `duckdb` binary cannot query `stg_restaurants`** — query `raw_restaurants` instead, or use Python.
> - **`dbt_utils.expression_is_true` at the column level prepends the column name.** The schema.yml form `columns: - name: latitude / tests: - dbt_utils.expression_is_true: expression: "..."` produces `where not(latitude <expr>)` which is a SQL parser error. **Attach range expressions at the model level**, not the column level. See `dbt/models/staging/schema.yml`.
> - **DuckDB Python UDFs need numpy.** With `null_handling='special'` you avoid the C-level NumPy buffer round-trip *most* of the time, but DuckDB still imports numpy on registration. We declare it as an explicit dependency in `pyproject.toml`. If you remove it, expect `'numpy' is required for this operation` at first invocation — not at install time.
> - **dbt selectors: the `path:seeds` form requires `cd`-ing into the project dir.** The orchestrator does (`cwd=dbt/`) so `path:seeds` resolves to `dbt/seeds/*` correctly. If you ever invoke dbt with `--project-dir dbt/` from outside, switch to `--select 'resource_type:seed'` instead — `path:` is path-relative and breaks.
> - **`_quality_flags` is a `LIST(VARCHAR)` and is never NULL.** `LIST_FILTER([...], x -> x IS NOT NULL)` returns `[]` (an empty list), not NULL. Downstream stages can rely on this contract; the schema.yml `not_null` test pins it.
> - **Place ID validation is intentionally lenient.** The seed `place_id_prefixes` only contains `ChIJ`-family prefixes — these match all 1068 of 1073 real-world rows. The 5 nulls are rows where the source CSV had no place_id. Suspect-looking ones (e.g., `ChIJEv9q3heFKRjZ8fpJAMNXy6t`, 28 chars) pass the validator because we can't tell from prefix + length alone whether they're fabricated. **Step 3 (dedup) catches these via geo+name conflict** — the dataset has at least 5 such cases where two rows have the same suspicious place_id but distinct names/coords.
> - **Real data signal at end of Stage 2** (1073 rows):
>   - Top flags: `missing_price_point=206`, `missing_address=108`, `missing_website=15`, `missing_place_id=5`, `missing_city=4`, `unknown_price_point=2`
>   - 22 distinct `city_canonical` values (matches seed exactly)
>   - 102 distinct `primary_type` values — the cuisine taxonomy in Step 4 needs to fold these
>   - URL canonicalization: 1058 of 1073 rows have a non-NULL canonical website; tracking params/fragments/case stripped uniformly
> - **Where to look:**
>   - UDFs (the heart of Step 2): `src/revel/dbt_plugin.py`
>   - Staging models: `dbt/models/staging/{stg_restaurants.sql, stg_restaurants__flagged.sql}`
>   - Seeds: `dbt/seeds/*.csv` + `dbt/seeds/schema.yml`
>   - Stats: `src/revel/clean.py` → `output/<run_id>/02_clean_stats.json`
>   - Tests: `tests/unit/test_dbt_plugin.py` + `tests/integration/test_pipeline_step2.py`
>   - To inspect staging output: **don't use the `duckdb` CLI** (UDFs aren't registered there). Use:
>     ```bash
>     uv run python -c "
>     import duckdb
>     from revel.dbt_plugin import register_udfs
>     c = duckdb.connect('data/revel.duckdb', read_only=True); register_udfs(c)
>     print(c.sql('SELECT * FROM stg_restaurants__flagged LIMIT 5').df())"
>     ```

**Goal**: Per-column normalization and a `_quality_flags` list column, fully expressed as SQL views. No LLM, no Python row processing, no Parquet output.

**Files**
- `dbt/models/staging/stg_restaurants.sql` — column-level cleaning (**view**)
- `dbt/models/staging/stg_restaurants__flagged.sql` — adds `_quality_flags` (**view**)
- `dbt/models/staging/schema.yml` — tests + docs
- `dbt/macros/canonicalize_url.sql` — chain of `regexp_replace` calls
- `dbt/seeds/{cuisine_taxonomy.csv, city_canonical.csv, price_point_mapping.csv, place_id_prefixes.csv}` — initial drafts (cuisine + romance refined in Step 4)

**Per-column rules** (DuckDB SQL):

| Column | Transform |
|---|---|
| `name` | Original preserved. New `name_core` = `lower(unaccent(regexp_replace(trim(name), '^the\s+', '', 'i')))` with whitespace collapsed and punctuation stripped. |
| `city` | Trim, strip surrounding quotes. `LEFT JOIN seed_city_canonical` on lowercased input → `city_canonical`. Unknown cities pass through; flagged. |
| `display_address` | Trim, collapse whitespace, strip trailing `, USA` / `, United States`. Extract `state_code` via `regexp_extract(display_address, '\b([A-Z]{2})\s+\d{5}', 1)` and `postal_code` via `regexp_extract(display_address, '\b(\d{5})(-\d{4})?\b', 0)`. |
| `google_place_id` | Trim. Validated: matches `^[A-Za-z0-9_-]{20,}$` AND prefix is in `seed_place_id_prefixes`. Failures → `NULL` + `'invalid_place_id'` flag. |
| `latitude`, `longitude` | Reject if outside US bbox (`lat ∈ [17, 72]`, `lon ∈ [-180, -65]`) or `(0, 0)` → `NULL` + `'invalid_coords'` flag. |
| `price_point` | `LEFT JOIN seed_price_point_mapping`. Unknowns → `NULL` + `'unknown_price_point'` flag. |
| `primary_type` | Lowercase + snake_case (already mostly is). Strip trailing `_us` / `_restaurant_us` into `region_hint`. |
| `website` | Macro `canonicalize_url`: lowercase scheme+host, strip `www.`, drop fragments + tracking params (`utm_*`, `gclid`, `fbclid`, `scid`, `y_source`, `ecid`, `icid`, `cmp`, `SEO_id`), URL-decode path, no trailing slash, keep first 2 path segments. Original preserved as `website_raw`. If macro proves brittle, fall back to dbt-duckdb's `python_function` (documented escape hatch). |

**Derived columns added**
- `geohash7` from valid lat/lng (~150m cell) — pure-SQL implementation in a macro
- `name_core`, `state_code`, `postal_code`, `region_hint`
- `_quality_flags: LIST(VARCHAR)` — built as `array_concat(...)` of conditional flag literals

**Tests in `schema.yml`**
- `not_null`: `id`, `name`, `name_core`, `_quality_flags`
- `accepted_values` for `price_point ∈ {low, medium, high}` (null allowed)
- `dbt_utils.expression_is_true` for lat/lon ranges (where not null)
- `dbt_utils.expression_is_true` for `length(google_place_id) >= 20 OR google_place_id IS NULL`
- `relationships`: `city_canonical` joins back to `seed_city_canonical.canonical`

**Output**: an updated DuckDB view inside `data/revel.duckdb`. To inspect: `duckdb data/revel.duckdb -c "SELECT * FROM main.stg_restaurants__flagged LIMIT 20"`. **No Parquet snapshot at this stage.**

**Risks / mitigations**
- *URL canonicalization in pure SQL is fragile*: pre-decided fallback to dbt-duckdb python function; cost ~1 hour to switch.
- *Over-aggressive name normalization breaks dedup of intentionally distinct venues* (e.g., `Carbone` vs `Carbone Vino Dallas`): keep `name` original; `name_core` only for blocking — geo + place_id remain co-signals.
- *Place_id false negatives*: log a sample of rejected place_ids in the run report.

## Step 3 — Deduplicate (Stage 3, dbt intermediate + Python helper)

**Goal**: Resolve duplicates with explicit, tunable rules; merge complementary fields; emit canonical records with provenance. Keep it simple with the tests. This is version 1 only.

**Architecture**
- Edge generation in dbt: `int_restaurants__dedup_edges.sql` (**view**) emits all match-pairs with tier + confidence
- Connected components in Python: `src/revel/dedup_clusters.py` reads edges from DuckDB, runs `networkx.connected_components`, writes a `dedup_cluster_map(id BIGINT, cluster_id BIGINT)` table back into the same DuckDB file
- Cluster merge in dbt: `int_restaurants__deduped.sql` (**table**) joins the cluster map and applies merge precedence

**Tier definitions**

1. **Tier A — exact `google_place_id`** (highest confidence; ~95% of detectable dups in the data).
   - Group by non-null cleaned `google_place_id`. Within-group pairs are matches. Confidence = 1.0.
2. **Tier B — geo + name match** (catches dups with fabricated/null place_ids).
   - Block by `geohash6` (~1.2km) ∩ same `city_canonical`.
   - Pairwise `rapidfuzz.token_set_ratio` ≥ **92** AND haversine ≤ **150m** AND (same `state_code` OR one null).
   - SQL implementation: candidate pairs from a self-join on `geohash6`; ratio + haversine via a dbt-duckdb python function (`udf_pair_score(name_a, name_b, lat_a, lon_a, lat_b, lon_b)` returning a struct).
   - Confidence = `0.85 + (ratio − 92) * 0.01`.
3. **Tier C — website match** — **disabled by default**, configurable in `local.yaml`. Catches missing-geo cases. Block on canonical website host+first-path-segment within same `city_canonical`. Confidence = 0.80. Off because chains (Uchi, Carbone, Le Jardinier) legitimately share websites.

Thresholds live under `dedup:` in `local.yaml` and pass into dbt via `--vars`.

**Cluster building (Python)**
- `dedup_clusters.py` reads `int_restaurants__dedup_edges` via DuckDB Python API, builds a graph with `networkx`, computes components, writes back the cluster map. Idempotent given the same edges.
- Run between `dbt build --select staging+ int_restaurants__dedup_edges` and `dbt build --select int_restaurants__deduped+`. Orchestrated by `pipelines/restaurant_pipeline.py`.
- Logged: edge count per tier, cluster size histogram, top 20 largest clusters.

**Merge rules** (`int_restaurants__deduped.sql`)
- Per cluster, pick by precedence:
  1. Non-null wins over null
  2. Most specific wins (longer `display_address`; address with state+zip > without)
  3. `price_point`: mode within cluster; ties broken `high > medium > low`
  4. `primary_type`: most specific via `seed_primary_type_specificity.csv` ranking + `arg_max`
  5. `website`: prefer canonicalized; keep longest `website_raw`
  6. `latitude`, `longitude`: median of valid values
- Provenance columns:
  - `canonical_id BIGINT` = `min(source_ids)` for stability across reruns
  - `source_ids LIST(BIGINT)` — every original `id` in the cluster
  - `dedup_confidence DOUBLE` — min confidence of any merge edge in the cluster
  - `dedup_tier VARCHAR` — `A`, `B`, `C`, or `singleton`
  - `_quality_flags LIST(VARCHAR)` — union across the cluster

**Tests in `intermediate/schema.yml`**
- `unique` on `canonical_id`
- `unique` on `google_place_id` where not null (post-dedup)
- `not_null` on `canonical_id`, `name`, `source_ids`
- `dbt_utils.expression_is_true` `array_length(source_ids) >= 1`
- Custom singular test: no cluster has rows from more than one `city_canonical`

**Outputs**
- `int_restaurants__deduped` table inside `data/revel.duckdb`
- `output/<run_id>/03_dedup_report.json`: tier counts, cluster size histogram, top-N clusters with member names, Tier C activations, geo-only matches with low ratio (for human spot-check)

**Tests (Python)**
- Unit tests for `dedup_clusters.py` with synthetic edges (chain `A–B–C`, isolated singletons, cycle).
- Regression fixture: known dups from the real CSV (Traif/traif, Dirt Candy x2, Ivan Ramen x3, Merois/The Merois, Antoine's Restaurant/Restaurnt, dLeña casing variants) — assert exact collapse counts.

**Judgment calls** (`docs/dedup-judgment.md`)
- Hotels are kept distinct from in-house restaurants even at the same address.
- Pop-ups inside another venue (e.g., `Colibrí Pop-up at Los Balcones`) are not merged with the host.
- Same place_id in different cities → cluster split by `city_canonical`, flagged.

**Risks / mitigations**
- *Over-merging chains*: Tier C off by default; Tier B requires name + geo together.
- *Under-merging due to bad place_ids*: Tier B catches it; report surfaces Tier-B-decisive clusters for spot-check.
- *Python step in the middle of a SQL pipeline feels off*: documented v1 wart in ADR-001; v2 with `dagster-dbt` makes it a first-class asset.

## Step 4 — Fill & enrich (Stage 4)

> **Status: ✅ Implemented.** Run `just pipeline-run --dry-run` to exercise without an API key. Live Gemini path requires `GEMINI_API_KEY` in `.env`; once set, the same command runs against the real LLM.
>
> **Implementation notes for the next dev**:
>
> - **Stage 4 is two distinct sub-stages.** 4a is dbt + seeds (deterministic). 4b is Polars + Gemini SDK (the only LLM step). They communicate through the single Parquet boundary at `data/pre_agent/restaurants.parquet` — that's the entire reason ADR-004 exists. Don't conflate them.
> - **Cuisine taxonomy is a closed `Literal[...]` in two places.** `dbt/seeds/cuisine_taxonomy.csv` and `src/revel/enrich/llm/schemas.py::CuisineLiteral` MUST stay in sync. If you add `Persian` to the SQL seed, you also add it to the Python literal — otherwise Gemini's structured output validation will reject every Persian classification it makes. There's a TODO to derive the Python literal from the seed at build time; for v1 it's a manual two-line edit.
> - **Romance composite weights live in TWO places too.** SQL composite is in `int_restaurants__enriched_det.sql`; Python composite is `DEFAULT_WEIGHTS` in `src/revel/enrich/romance.py`. Keep them aligned. If you make weights configurable via `local.yaml` later, the SQL composite needs to read from `--vars` and the Python one from `Settings`.
> - **Stub LLM client returns `Other` with confidence 0.5 for cuisine.** That's *intentionally* below the 0.6 confidence threshold so dry-runs end up with NULL cuisine for LLM-needed rows (44.7% of the dataset). Don't be fooled into thinking the live Gemini run will produce that null rate — the stub is a no-op for cuisine. For romance the stub returns mid-range scores (5,5,5,5,5) which DO survive (no confidence threshold on romance).
> - **The deterministic cuisine + romance seeds were tuned to the v1 dataset.** With the seeds shipped, ~55% of rows get cuisine deterministically and ~46% get romance deterministically. The remainder escalates to Gemini. If a future dataset has different `primary_type` distribution, expand `cuisine_taxonomy.csv` and `romance_rubric.csv` rather than asking the LLM to do more work.
> - **`romance_rubric.csv` joins on `(primary_type, price_point)`.** A duplicate row in this seed will cause `int_restaurants__deduped` to fan-out and the post-dedup `unique` test to fail. I learned this the hard way (had `french_restaurant,low` twice). Run `awk -F',' 'NR>1{print $1","$2}' dbt/seeds/romance_rubric.csv | sort | uniq -d` to check.
> - **External Parquet boundary path is env-driven.** `dim_restaurants__pre_agent.sql` reads `REVEL_PRE_AGENT_PARQUET` so the orchestrator can point it at any tmp dir during tests. dbt-duckdb's `external_location` config is *not* relative to the project dir — it's relative to the cwd at runtime — so the env-var indirection makes things deterministic.
> - **LLM cache is on by default.** First Gemini run on a given dataset will cost real money (proportional to the number of rows that escalate). Reruns are free + deterministic. The cache lives at `.cache/llm/`, gitignored. Cache key includes `SCHEMA_VERSION` from `enrich/llm/schemas.py` — bump that constant if you change prompts or output schemas, otherwise stale responses leak into new runs.
> - **`dry_run=True` always uses `StubLLMClient`.** Tests + CI don't need credentials. The orchestrator's `make_client()` enforces this.
> - **Security: prompts are NEVER logged.** Only counts and token totals (per `security-rules.md`). The stub prints "stub: deterministic mid-range score" as the rationale; that's a marker so analysts can grep the published Parquet for stub-derived rows.
> - **Real data signal at end of Stage 4** (with `--dry-run`):
>   - 987 rows total (post-dedup)
>   - Cuisine: 546 deterministic, 0 resolved by stub-LLM (all 441 LLM rows are "low confidence" = NULL + flag), 0 failed
>   - Romance: 459 deterministic, 528 resolved by stub-LLM, 0 failed
>   - Distribution leaders (deterministic): American 107, Japanese 96, Italian 73, French 39, Steakhouse, Mexican, Korean, etc.

### Step 4a — Deterministic enrichment (dbt intermediate + mart)

**Files**
- `dbt/models/intermediate/int_restaurants__enriched_det.sql` (**table**)
- `dbt/seeds/cuisine_taxonomy.csv` — `primary_type` → `cuisine` (closed taxonomy ~20 categories)
- `dbt/seeds/cities_by_geohash5.csv` — precomputed `geohash5 → city_canonical, state_code` from offline `reverse_geocoder` (built once by `scripts/build_city_seed.py`, committed to the repo so the pipeline doesn't need network for geocoding)

**Logic**
- City fill: rows with null `city_canonical` and valid lat/lng → join on `geohash5` against `cities_by_geohash5`. Misses stay null + flagged.
- State / postal re-derivation: re-extract from any `display_address` that became non-null after merge.
- Cuisine — Stage 1 (rule-based): `LEFT JOIN seed_cuisine_taxonomy` on `primary_type`. Output `cuisine` + optional `cuisine_secondary`. Generic types (`restaurant`, `fine_dining_restaurant`, `bistro`, `hotel`, `bar`, `cafe`) intentionally yield NULL → flagged with `_needs_llm_cuisine = TRUE`.
- Romance — Stage 1 (rubric, deterministic): rows with high-signal `primary_type` + non-null `price_point` get a deterministic 5-sub-score row from a `seed_romance_rubric.csv` lookup, plus the composite. Otherwise `_needs_llm_romance = TRUE`.

**Mart**
- `dim_restaurants__pre_agent.sql` — selects final pre-agent columns including `_needs_llm_cuisine` and `_needs_llm_romance`. Materialized as **`external` Parquet** at `data/pre_agent/restaurants.parquet`. This is the only intermediate Parquet boundary in v1; Python reads it via `pl.read_parquet` without holding a DuckDB connection.

**Tests in `marts/schema.yml`**
- `not_null` on `canonical_id`, `name`
- `accepted_values` on `cuisine` (allow null) against the taxonomy
- `dbt_utils.expression_is_true` `_needs_llm_cuisine = (cuisine IS NULL)` — invariant
- `unique` on `canonical_id`

### Step 4b — Python LLM enrichment (Gemini)

**Files**
- `src/revel/enrich/cuisine.py`, `src/revel/enrich/romance.py`, `src/revel/enrich/fills.py`
- `src/revel/enrich/llm/{client.py, cache.py, schemas.py}`

**LLM client contract**
- `LLMClient` Protocol: `complete_json(prompt, response_schema, max_retries=2) -> dict`
- `GeminiClient` impl: `google-genai` SDK, model `gemini-2.0-flash`, `temperature=0`, `response_mime_type="application/json"`, `response_schema=<Pydantic model>`. The SDK enforces the schema; we additionally `model_validate` the result for defense in depth.
- `StubClient` impl for tests / `--dry-run`: deterministic canned outputs keyed off input shape; never calls the network
- `diskcache`-backed cache (`.cache/llm/`), key = `sha256(provider + model + prompt + schema_version)`. Reruns are free + deterministic.
- Concurrency: `asyncio.Semaphore(llm_max_concurrency)`; default 4.
- **Logging**: counts and token totals only; never log prompt content (security). Log redaction enforced in `logging_setup.py`.

**Cuisine fallback (`cuisine.py`)**
- Process only rows with `_needs_llm_cuisine == TRUE`
- Batch 20 rows per call. Inputs per row: `name`, `name_core`, `primary_type`, `website` host, `city_canonical`, `display_address`
- Output schema (Pydantic): list of `{canonical_id, cuisine: Literal[...], cuisine_secondary: Optional[Literal[...]], confidence: float}`
- Confidence < 0.6 → leave null + `'low_llm_cuisine_confidence'` flag
- Retry once on validation failure; final failure → null + flag

**Romance scoring fallback (`romance.py`)**
- Process only rows with `_needs_llm_romance == TRUE`
- Batch 20 rows per call. Inputs include `cuisine` (now resolved) and `price_point`
- Output schema: list of `{canonical_id, ambiance, intimacy, quietness, dining_experience, cuisine_fit, rationale: str}`, each sub-score `int ∈ [0, 10]`
- Composite: `0.25 ambiance + 0.20 intimacy + 0.15 quietness + 0.20 dining_experience + 0.20 cuisine_fit`, scaled to `[0, 100]`. Weights configurable in `local.yaml`.
- Out-of-range scores → retry once → on failure, fall back to deterministic rubric with `'romance_llm_failed'` flag

**Output**
- `data/enriched/restaurants.parquet` — full post-agent dataframe (cuisine, cuisine_secondary, romance_score, romance_subscores, romance_rationale)
- `output/<run_id>/04_enrichment_report.json` — cuisine distribution (rule vs LLM), score histogram, LLM cache hit rate, token totals, estimated cost

**Tests**
- Cuisine: every `primary_type` in the input either maps deterministically or is in the "escalate" set — pinned via parameterized test
- Romance: golden file on 20 representative rows; assert score deltas stay within tolerance when sub-score weights change predictably
- LLM: `StubClient` in CI; live path gated by `LIVE_LLM=1` env

**Risks / mitigations**
- *Hallucinated cuisine outside taxonomy*: closed-set enforced by `Literal[...]` + Gemini `response_schema`; on violation, retry → null + flag
- *Cost blowup*: cache + batching + dry-run; report estimated cost before live calls; configurable confirmation prompt above a threshold (default $2)
- *Subjectivity of romance score*: rubric documented (`docs/romance-scoring.md`), weights configurable, sub-scores + rationale preserved so consumers can re-weight
- *Gemini API outage*: with cache populated, reruns work offline; first run with no cache will fail at the LLM step — `--dry-run` is the unblock

> - **Validation is fail-closed.** Any error (per `validate.py`) aborts publish. A separate `output/run_report.md` is still written so you can see *why*. The pipeline raises `RuntimeError` with the report path; the CLI surfaces it.

> - **Validation is intentionally column-shape-only.** No row-level data quality assertions beyond what `architecture-decisions.md` §6 requires (closed-set enums, range checks, primary key uniqueness). 3. **Cuisine taxonomy granularity** — ✅ Decision: **hybrid, ~20 categories**. The plan (Step 4a) was already a hybrid: deterministic `LEFT JOIN seed_cuisine_taxonomy` covers ~85% of rows (the ones whose Google `primary_type` is itself a cuisine, e.g. `italian_restaurant` → `Italian`). Only rows with generic types (`restaurant`, `fine_dining_restaurant`, `bistro`, `hotel`, `bar`, `cafe`) escalate to Gemini, which is given **the same closed taxonomy as a `Literal[...]` constraint** so it cannot invent categories. **Why not coarser**: a 10-category taxonomy would over-cluster (Japanese omakase, ramen, izakaya all collapse to "Asian"). **Why not finer**: subdividing Japanese into Sushi/Ramen/Izakaya makes the LLM's job harder (each call now has more options to disambiguate) and downstream consumers will rarely use the finer cuts. The taxonomy lives in `dbt/seeds/cuisine_taxonomy.csv` and a single edit there can re-shape every row in the next pipeline run.
